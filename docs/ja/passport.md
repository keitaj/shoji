# パスポート: 確認できたこと

[English](../passport.md) | **日本語**（英語版を正とする）

shoji はマイナンバーカードから証明を作る。この文書は、日本の IC 旅券で同じことができるかを調べた記録。
**パスポート用の回路は存在しない。** あるのは読み取り機能（`ios/` の開発用ツール）と、パスポートの署名の構造を
中身を出さずに表示する `cmd/sodinspect` だけ。

## 実物のパスポートで確認したこと

最近発行された日本のパスポート1冊を、2026年11月23日に NFC（BAC）で読んだ。読んだのは、署名の領域、
チップの公開鍵、セキュリティ情報、チップによる署名1つだけ。顔写真と、氏名などの入った領域は読んでいない。

| 項目 | 観測した内容 |
|---|---|
| 署名用証明書の発行者（CSCA） | `CN=e-passportCSCA, OU=The Ministry of Foreign Affairs, O=Japanese Government, C=JP` |
| 署名用証明書（Document Signer） | CSCA が ecdsa-with-SHA384 で署名。鍵は EC P-384（曲線パラメータを明示する形式）。有効期間は約11年 |
| 署名の領域への署名 | ecdsa-with-SHA384 |
| データグループのハッシュ | SHA-384 |
| 署名の対象のデータグループ | DG1, DG2, DG13, DG14, DG15 |
| 能動認証（Active Authentication） | 対応。ECDSA P-384、8バイトの乱数の SHA-384 に対する plain 形式（`r \| s`）の署名。チップの鍵（DG15）は署名の対象に含まれる |
| アクセス制御 | BAC で読めた。DG14 は PACE（ECDH generic mapping、AES-256）にも対応と示している |
| Chip Authentication | 示されていない |

すべての検査が通った: データグループから署名付き属性までのハッシュの連鎖、署名用証明書の鍵による署名、
新しい乱数に対するチップの署名。署名用証明書を CSCA の鍵で検証することはできていない（CSCA の証明書はチップに入っていない）。

古いパスポートは別の方式かもしれない。期限切れのパスポートは読めなかった（失効時にチップが破壊される）。

## 資料から

- 日本の旅券冊子用 IC のプロテクションプロファイル（外務省旅券課、JISEC 認証）は、BAC・PACE・能動認証を対象とする。
  これに準拠した2020年のチップ製品は、能動認証を ECDSA（256ビットと SHA-256、または 384ビットと SHA-384）で実装している。
- 読み取り機能は ICAO Doc 9303 第8版（Part 3, 10, 11）に従う。テストは Part 11 Appendix D の計算例を再現する。

## パスポート用の回路に必要なもの

マイナンバーカードと同じ主張ができる: データは国が署名している、証明者がチップを持っている（能動認証が、
カードによる nonce への署名の役割を果たす）、条件は署名済みのデータから判定する（国籍を含む）。

ただし、今の回路よりかなり重くなる。

- ECDSA P-384 の検証が3回（CSCA → 署名用証明書、署名用証明書 → 署名の領域、チップ → 乱数）。Noir の組み込みの
  検証機能は256ビットの曲線だけなので、P-384 は多倍長演算で行う必要がある
- ハッシュの連鎖のために SHA-384 を数回
- 能動認証の乱数は8バイトしかないので、検証サーバのチャレンジと `app_id` をそこに圧縮する必要がある
  （今のカードの署名はハッシュ全体に結びつくが、こちらは64ビット）
- CSCA の証明書はチップの外（公開されているマスターリスト）から得る必要がある

端末で実用的に動くかは測っていない。

## 関連する取り組み

[zkPassport](https://github.com/zkpassport/circuits) はパスポート用の Noir の回路をオープンソース（Apache-2.0）で公開しており、
日本のパスポートを対応済みとしている。確認した時点（2026年11月）では、回路は能動認証を使っていないようだった。
また、コードには検証方式として「日本のマイナンバーカード（JPKI）」が予約されているが、その時点の公開リポジトリに
該当する回路は無かった。
