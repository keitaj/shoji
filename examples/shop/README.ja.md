# 例: shoji を組み込んだお店

[English](README.md)

架空のオンラインショップ「こもれび商店」。別のサービスが shoji を組み込むときと同じ形で使っている。
会員登録はなく、お店は利用者が誰なのかを知らない。それでも次のことができる。

- 数量限定の品を**1人1点**だけ売る（転売・買い占め対策）
- レビューを**購入者だけ、1つの品につき1人1件**に限る（やらせレビュー対策）
- 運営者が**利用者を停止**できる。停止された人は、やり直しても戻れない
- **保存しているデータをすべて**見せられる。nullifier、購入、レビューだけで、氏名・住所・生年月日・メールアドレスは無い

実際の販売は行わない。これはデモであり、そのまま運用するものではない（「制限」を参照）。

## 検証サーバの組み込み方

お店は自分用の検証サーバを動かし、2つのリクエストだけでやり取りする。
スマートフォンが通信する相手は検証サーバだけで、お店は証明を見ない。

```
 ブラウザ           お店                     検証サーバ               スマートフォン
    │ 「購入」        │                          │                       │
    │ ──────────────▶ │ POST /sessions           │                       │
    │                 │ ───────────────────────▶ │                       │
    │ ◀── QR コード ─ │ ◀── セッション、リンク ─ │                       │
    │                 │                          │ ◀ 読み取り、カード、証明 │
    │ 問い合わせ      │ GET /sessions/<id>       │                       │
    │ ──────────────▶ │ ───────────────────────▶ │                       │
    │ ◀── 結果 ────── │ ◀── 確認済み、nullifier  │                       │
```

セッションが確認済みになると、お店はその人の nullifier を受け取り、それをどう扱うかを決める
（[`shop.go`](shop.go) の `decide`）。この nullifier はすでにこの品を買ったか、レビューを書いたか、停止中か。
組み込みはこれで全部である。

nullifier は検証サーバのオリジンごとに決まるので、サービスごとに専用のオリジンが必要になる。
1つのオリジンを2つのサービスで共有すると、同じ人に同じ nullifier が見える。

## カードなしで動かす

`make circuit` で作られるモックCAを使う。

```sh
go run ./cmd/verifier -public-origin http://127.0.0.1:8080 -trusted-ca testdata/ca.pem &
go run ./examples/shop          # http://127.0.0.1:8090
```

お店を開いて「購入する」を押し、QR コードの下の「カードなしで試す」を開いて、リンクをモックの保有者に渡す。

```sh
go run ./cmd/mockclient -link 'shoji://verify?u=...&s=...'
```

同じ品でもう一度実行すると断られる。別の人は `-cert testdata/adult2.pem -key testdata/adult2.key`。
`minor` は受理される証明を作れない。運営者の画面は `/admin`。

## AI エージェントからの注文

先行入場券は、利用者の代わりに動くソフトウェアからも注文できる（あかりは不可）。エージェントの注文には委任による証明が付き、
お店は本人のカードと同じ nullifier を受け取る。そのため、エージェントが何体いても1人1点の制限が効く。

```sh
go run ./cmd/verifier -public-origin http://127.0.0.1:8080 -trusted-ca testdata/ca.pem \
    -delegated-vk circuits/target/vk_delegated/vk &
go run ./examples/shop &
go run ./cmd/wallet delegate          # 「カードをかざす」に当たる操作。モックのカードが委任に署名する
go run ./cmd/wallet serve &           # 利用者のウォレット。手元のエージェントから渡されたリンクに答える
go run ./examples/agent -product ticket -n 10
```

エージェント10体で、購入は1件。その後に同じ人が（モックの）カードで来ても、購入済みと言われる。
運営者の画面には、注文したのが本人かエージェントかが出る。エージェントに AI のモデルは入っておらず、証明書も委任も証明も見ない。
お店のリンクをウォレットに渡すだけである。ウォレットの代役がまだやっていないのは判断で、渡されたリンクすべてに答える。

## 実カードで動かす

[トップの README](../../README.ja.md) のとおりに検証サーバを起動し（ローカルネットワークで待ち受け、本物の署名用CAを信頼）、
お店を `-verifier http://127.0.0.1:8080` で起動する。QR コードは [`ios/`](../../ios/README.md) のアプリで読み取る。
お店自体はループバックのままでよい。お店と通信するのは、このマシンのブラウザだけである。

## 制限

- 状態はメモリ上にあり、お店を止めると消える。検証サーバは自分のデータベースを持つが、お店はそれを使わない。
- `/admin` にログインは無い。お店はループバックで動かすこと。
- 検証サーバの `POST /sessions` は、到達できる人なら誰でも呼べる。
- 他人の QR コードを見せられて確認を完了すると、その購入は QR コードを表示していたブラウザの人のものになる。
  [脅威モデル](../../docs/ja/threat-model.md)にあるセッションの乗っ取りである。
- nullifier は証明書の再発行で変わる。制限が効くのは証明書ごとであり、生涯ではない（[未解決の点](../../docs/ja/open-questions.md)）。
- 操作のたびにカードをかざす必要がある。実際のサービスなら、一度確認したあとは nullifier に結びつけたログインセッションを使うだろう。
